# Project 3: Deploying and Extending Your Own Coding Agent

## Learning Goals

- Learn how to deploy a full-stack, AI-powered application using containers and a reverse proxy
- Practice designing a new feature for an existing codebase: requirements, architecture, tradeoffs, and a testing strategy
- Gain hands-on experience with analysis tools, including setting up, customizing, and using them
- Practically assess and compare the costs and benefits of existing static and dynamic bug-finding tools
- Integrate CI tooling into development practice using GitHub Actions

## Project Context

Your team has been building on [OpenCode](https://opencode.ai/), an open-source AI coding agent. Until now, the agent has only ever run on your own laptops, inside your own terminals. That is fine for the people who built it, but it is not how a product gets into the hands of real users.

Your manager has assigned you three major tasks.

Firstly, you will **run your team's own coding agent** on a server so that anyone with a browser (within CMUQ's network) can reach it. In other words: your team is going to run its own coding agent as a service.

Secondly, you will **implement a new feature**, which may be an extension of the feature(s) you implemented in Project 2. Before implementation, you will need to submit a design document that convinces your manager it is worth building.

Thirdly, because an agent that writes code needs to be held to a high standard itself, you will **evaluate existing analysis tools** beyond simple linting or unit testing, produce a comparison of their costs, benefits, and risks, and **integrate at least one into your CI pipeline** so that every change to your agent is checked automatically.

## P3A: Checkpoint Deliverables

## Deployed OpenCode Application (25 pts)

Your team will be using Linux Virtual Machines (VMs) hosted at CMUQ to deploy your own instance of OpenCode. You will package your team's OpenCode version with **Docker**, put **Nginx** in front of it as a reverse proxy, and verify that you can reach your agent remotely from a browser. Further instructions on how to deploy can be found [here](deployment.md).

At a high level, a successful deployment looks like this:

- Your OpenCode instance builds and runs inside a Docker container on your team's VM
- Nginx accepts incoming browser traffic and forwards it to the OpenCode server running in the container
- A teammate who is **not** on the VM can open the site in a browser from their own laptop (within CMUQ's network) and start a session with the agent

Once you have successfully deployed your agent, make sure to test within your team that it actually does useful work end to end: connect it to a model provider, open a project, and ask it to make a small change.

By the checkpoint deadline you should:

- Submit a link to the deployed site on Gradescope. The link should be in the form http://<VM_HOSTNAME>:<PORT> (e.g, http://crs-17313-demo-gpu.qatar.cmu.edu:8080)
- Make sure your deployment files (e.g., `Dockerfile`, `docker-compose.yml`, Nginx configuration) are committed to your repository, with no secrets in them

### Analysis Tool and CI Integration (15 pts)

An agent that writes code for other people should itself be well-tested and trustworthy. Before jumping into tool integration, your manager would like you to research what existing analysis tools are out there that can be used with OpenCode, and then wire at least one of them into your team's GitHub workflow.

#### Step 1: Explore the tools

First, identify and experiment with **at least N potential static and dynamic analysis tools** that are applicable to your system, where N is the number of people in your team. We provide a [starter list of tools](#starter-list-of-tools) in the resources section below to help you get started, but you are not limited to these tools.

In your selection of tools, you should

- have **at least one** static analysis tool
- have **at least one** dynamic analysis tool
- have **at least one** tool that is not from our starter list
- **Do not use** any of the analysis, linting, or testing tools that already ship with OpenCode as part of your analysis

For each tool that you assess

1. Create a separate testing branch in your repository (named appropriately for the tool you're testing) to integrate the tool into your project and test out its capabilities

2. Create a pull request to the main branch from each of these testing branches. The PR should have:
    - **Concrete evidence that you had successfully installed the tool** through trackable file changes demonstrating that extra files/packages were installed.
    - **Artifacts that demonstrate that you have successfully run the tool on your repository.** Acceptable artifacts include output files generated by the tool, or a text file containing the terminal output from the tool; you may also attach screenshots as additional pieces of evidence. They can be attached to the Pull Request in either the description or follow-up comments.

!!! note "Grading Note"
    We will not be grading the quality or quantity of any code you put into these testing branches/PRs, just the evidence that you have successfully installed and run the tool.

#### Step 2: Compare the tools

In your evaluations, consider & experiment with the types of customization that are appropriate or necessary for this tool, both a priori (before it can be used in your project) and over time. Assess the strengths and weaknesses of each tool/technique, both quantitatively and qualitatively.

Write up a comparison of your tools covering, at a minimum:

- **Benefits**: What types of problems does this tool catch, and how useful were the findings?
- **Limitations**: What does it miss, and what doesn't it support (e.g., parts of the codebase, the runtime or language features OpenCode relies on)?
- **False positives**: Were there many false positives? False negatives? True positive reports about things you don't care about?
- **Configuration effort**: How much work was it to install, configure, and run? How much customization was necessary?

For each tool, include its name, a one-line description, whether it is static or dynamic, a link to its documentation, and a link to the PR from its testing branch.

!!! tip "Tool Evaluation"
    There are a lot of different factors to consider when evaluating a tool. We recommend discussing with your teammates and deciding on a group of metrics to focus on when performing evaluations. A side-by-side table is a good way to present your comparison.

!!! tip "Time Management"
    Don't spend too long exploring. Set deadlines within your team to ensure that you have enough time for the feature implementation and the CI integration.

#### Step 3: Select and integrate a tool

Select **at least one** tool from your exploration and justify your choice in a short paragraph that refers back to your comparison. You **must recommend at least one tool**, even if it's with reservations.

Then fully integrate the selected tool into your project's workflow by creating a new **GitHub Actions** workflow that runs it as part of the development cycle. Your team should discuss:

- How often should this new integration be run (on each pull request? on commits to main?)
- What level of customization is needed for this tool?
- How should the integration of this tool be enforced?

To be considered successfully integrated, the tool must:

- Be **merged into your main branch**
- **Have been run at least once in the Git flow cycle** (i.e. either during the pull request, merge, or commit stage).
- **Pass** when run on your codebase. This is indicated by having a green checkmark.

!!! note "Ensuring Passing Checks"
    In order to ensure your checks pass successfully, you may have to make additional changes to your repository, such as fixing reported issues or tweaking tool configuration. Briefly document these changes and your reasoning in your comparison write-up.

!!! warning "Failing CI builds"
    Continually failing builds show you have *not* completely integrated the tool into your workflow.

On Gradescope, submit

- a link to your repository,
- links to the **N pull requests** for your tool-testing branches,
- your tool comparison write-up, and
- a link to one of the **successful GitHub Actions runs** for your integrated tool.

## Resources & Documentation

### Starter List of Tools

OpenCode is built in TypeScript and runs on the Bun runtime. Below are non-exhaustive lists of analysis tools that are available. Some tools may need adapting to work with this stack, and figuring out how much effort that takes is part of your evaluation!

For other resources, [Software Testing Magazine - Open Source JavaScript Code Analysis](https://www.softwaretestingmagazine.com/tools/open-source-javascript-code-analysis/), [Awesome Static Analysis page](https://github.com/analysis-tools-dev/static-analysis), and [Awesome Dynamic Analysis page](https://github.com/analysis-tools-dev/dynamic-analysis) have extensive listings of available static and dynamic analysis tools for a pretty hefty list of programming languages.

Some of the tools already have existing GitHub Actions workflows on GitHub Marketplace; use your Googling skills, and see what you find!

#### Static Tools

- [Semgrep](https://semgrep.dev/docs/): Pattern-based static analysis for finding bugs and security issues
- [CodeQL](https://codeql.github.com/docs/): Query-based code analysis, with built-in GitHub Actions support
- [Knip](https://knip.dev/): Finds unused files, exports, and dependencies in JavaScript/TypeScript projects
- [dependency-cruiser](https://github.com/sverweij/dependency-cruiser): Validates and visualizes module dependencies
- [OSV-Scanner](https://google.github.io/osv-scanner/): Finds known vulnerabilities in your project's dependencies

#### Dynamic Tools

- [Stryker Mutator](https://stryker-mutator.io/): Mutation testing tool for JavaScript/TypeScript
- [fast-check](https://fast-check.dev/): Property-based testing for JavaScript/TypeScript
- [k6](https://github.com/grafana/k6): Open source tool for load testing (for example, against your deployed server)
- [OWASP ZAP](https://www.zaproxy.org/): Scans a running web application for security vulnerabilities
- [Jazzer.js](https://github.com/CodeIntelligenceTesting/jazzer.js): Coverage-guided fuzzer for JavaScript/TypeScript
